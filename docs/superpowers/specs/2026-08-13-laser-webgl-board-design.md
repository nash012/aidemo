# 镭射棋盘 WebGL 3D 升级设计

## 目标

在保留当前原生微信小游戏工程、现有主界面、规则、AI、触摸流程和游戏状态的前提下，将镭射棋盘区域升级为真正的 WebGL 3D 渲染，并使用用户提供的 10 个独立 GLB 棋子模型。

不新建 Cocos Creator 工程，不接入 Cocos Runtime、Three.js 或其他完整 3D 引擎。WebGL 不可用或资源加载失败时，自动退回当前 Canvas 伪 3D 棋盘，确保游戏仍可操作。

## 已提供资源

- `cocos_chess_glb_models.zip`：10 个独立模型及总览资源。
- `model_manifest.json`：模型尺寸、顶点、三角面和材质统计。
- `README_CocosCreator.md`：坐标、单位、轴心和结构说明。
- `build_cocos_glb_models.py`：模型生成源脚本。
- `all_pieces_overview.glb`：只用于人工检查，不进入正式游戏资源。

模型采用 glTF 2.0 Binary、右手坐标系、Y 轴向上、米制单位、底部中心轴心，材质使用内嵌 Metallic-Roughness PBR 参数，无外部贴图、骨骼或动画。

## 总体架构

### 双画布分层

现有主 Canvas 继续使用 2D 上下文，负责：

- 主界面、阵型和难度选择；
- 状态栏、按钮、提示和规则弹窗；
- 返回确认与其他 2D 交互；
- 将 WebGL 画布的结果合成到棋盘区域。

新增一个透明离屏 Canvas，获取 WebGL 上下文，只负责：

- 10×8 棋盘、格线及红白禁区；
- GLB 棋子实例；
- 选中、落点和电脑动作提示；
- 3D 激光及棋子动画。

每帧先渲染离屏 WebGL 场景，再由主 2D Canvas 将其绘制到棋盘区域，之后覆盖现有界面。界面和棋盘可以独立演进，不把现有 UI 重写为 WebGL。

### 单一游戏状态

当前 `G.pieces`、回合、阶段、动作和激光路径继续是唯一事实来源。WebGL 层只读取这些状态并生成实例变换，不复制走棋、交换、反射、禁区或 AI 逻辑。

现有棋子类型映射到模型：

| 现有类型 | GLB 文件前缀 |
| --- | --- |
| `laser` | `laser_cannon` |
| `king` | `king` |
| `shield` | `shield` |
| `mirror` | `single_mirror` |
| `switch` | `double_mirror` |

阵营使用模型文件自带的红蓝版本，不在运行时强制换色。

## 轻量 WebGL 渲染器

只实现这批 GLB 和当前棋盘所需能力：

- GLB 2.0 容器解析；
- `POSITION`、`NORMAL` 和索引数据；
- 场景节点及局部变换；
- 内嵌 `baseColorFactor`、`metallicFactor`、`roughnessFactor`；
- 透视相机、深度测试、背面处理和透明清屏；
- 一套共享的卡通 PBR 近似着色器；
- 网格及材质 GPU 缓存。

不实现贴图、蒙皮、动画、形态键、扩展格式、实时环境反射或通用 glTF 编辑能力。遇到本项目未支持的必要数据时，整个 WebGL 棋盘初始化失败并进入伪 3D 回退，不能只显示部分模型。

## 3D 场景

### 棋盘

- 棋盘为 10×8 立体薄板，格子与现有行列坐标一一对应。
- 每格具有轻微高度、深色描边和可辨认的明暗差异。
- 红、白禁区位于棋盘表面底层，覆盖的格子必须与 `isZoneAllowed` 等现有规则完全一致。
- 棋子底部中心落在格子中心，统一缩放到不遮挡相邻格子的尺寸。

### 相机与灯光

- 阵型预览使用固定斜俯视相机，保证整个棋盘及具体阵型清晰可见。
- 实战沿用当前单指旋转、双指缩放和范围限制；相机状态只保留一套。
- 使用固定主光和低强度环境补光，突出低多边形卡通切面。
- 使用低成本的棋子脚下接触阴影，不使用动态阴影贴图。

### 棋子与方向

- 炮口、盾面和镜面必须与游戏逻辑方向一致。
- GLB 模型初始朝向通过每类模型的校准角定义，再按棋子的四个方向每次旋转 90°。
- 移动、旋转、互换和电脑操作动画复用现有动作时间线，仅将当前姿态转换为 3D 实例矩阵。

## 镜面语义

### 单面镜

`single_mirror_*.glb` 中浅蓝色的 `Mirror_Face` 是唯一反射面。模型保持竖直三棱柱结构：上下两块平行全等三角形、三块竖直长方形侧面。

运行时根据 `Mirror_Face` 的几何法线和模型校准角，计算四个棋子方向下的世界法线，并逐一与现有 `MIRROR_MAP` 反射结果核对。非镜面侧的视觉朝向不能被误认为反射面。棋规仍由现有逻辑决定，渲染器不另写一份反射规则。

### 双面镜

`double_mirror_*.glb` 中 `Mirror_Front` 与 `Mirror_Back` 都是反射面。其视觉朝向按四方向旋转，并与现有斜杠/反斜杠反射逻辑保持一致。

镜面的高光只做材质表现，不做实时场景反射，以控制移动设备性能。

## 激光与点击

- 激光路径继续由现有 `simulateLaser` 结果生成。
- WebGL 将每两个路径点转换为棋盘上方的 3D 发光带，包含亮色核心和半透明外层辉光。
- 激光在镜面处的转折点与逻辑格子中心完全一致。
- 点击棋盘时，根据 WebGL 相机和触摸坐标生成射线，与棋盘平面求交后换算为行列。
- UI 按钮与弹窗仍优先由 2D 层处理；只有未被 UI 消费的棋盘触摸才进入 3D 拾取。
- 回退模式继续使用当前伪 3D 投影和点击判定。

## 资源加载与生命周期

- 将 10 个独立 GLB 放入 `games/laser/models/`；总览 GLB 不进入正式游戏。
- 启动镭射模块时异步读取模型；加载期间显示现有背景和简短加载提示。
- 每个 GLB 只解析、上传 GPU 一次；同类同阵营棋子实例复用缓存。
- 退出镭射模块时释放 WebGL Buffer、Program 和上下文相关引用，并取消尚未完成的资源回调。
- 再次进入时允许重新初始化；失败原因只记录一次，避免每帧重复报错。

## 性能与兼容

- 优先获取 WebGL；不假设完整浏览器 DOM API 存在。
- 按设备像素比限制离屏渲染尺寸，最高 DPR 为 2，并只覆盖棋盘实际区域。
- 不使用实时阴影、后处理、贴图、骨骼、动画或反射探针。
- 正式场景不加载总览模型。
- 以下任一情况触发整套回退：无法创建 WebGL 上下文、着色器编译/链接失败、模型缺失或解析失败、必要 GPU 资源创建失败、合成 WebGL 画布失败。
- 回退后 UI、规则、AI、触摸、返回和重新开始保持可用。

## 文件边界

计划中的职责划分：

- `game.js`：创建主 2D Canvas，并向镭射模块提供创建离屏 Canvas 的能力。
- `games/laser/laser-game.js`：保留游戏状态和交互，选择 WebGL 或伪 3D 渲染路径。
- `games/laser/webgl-renderer.js`：WebGL 场景、相机、实例、拾取、激光和生命周期。
- `games/laser/glb-loader.js`：最小 GLB 解析和资源读取。
- `games/laser/models/*.glb`：10 个正式模型。
- `tests/laser-ai.test.js`：现有规则、AI 和交互回归。
- `tests/laser-webgl.test.js`：GLB、方向、状态同步和回退的最小测试。

不为本次迁移拆分现有完整游戏逻辑，也不修改其他两个小游戏。

## 测试与验收

### 自动测试

1. 10 个 GLB 均存在，文件头、声明长度和 JSON/BIN 分块有效。
2. 每类红蓝模型映射正确，必需网格、法线、索引和材质可读取。
3. 单面镜仅识别 `Mirror_Face`，双面镜识别前后两个镜面。
4. 单面镜和双面镜四个方向的世界法线与现有反射表一致。
5. 10×8 棋盘坐标、红白禁区和屏幕拾取映射正确。
6. 移动、旋转、互换和 AI 动画更新实例姿态但不修改规则结果。
7. WebGL、着色器和模型故障都进入完整伪 3D 回退。
8. 原有 AI、走棋、双面镜跨阵营互换、禁区、返回确认和定时器清理测试继续通过。

### 人工验收

在微信开发者工具及至少一台真机检查：

- 五种阵型预览可清楚辨认所有 3D 棋子；
- 红蓝棋子、红白禁区、炮口、盾面和镜面方向正确；
- 移动、旋转、互换、电脑动作和激光动画清楚连贯；
- 单面镜只有浅蓝镜面表现为反射面；
- 旋转/缩放视角、返回、重开及规则弹窗正常；
- 强制 WebGL 失败后旧棋盘可正常完成一局。

## 完成标准

- 支持 WebGL 的设备默认显示新 GLB 3D 棋盘。
- 不支持或初始化失败的设备自动显示旧伪 3D 棋盘。
- 所有现有玩法规则和 AI 行为无回归。
- 自动测试、语法检查和差异检查通过。
- 微信开发者工具与真机人工验收均有明确结果，不以桌面浏览器截图代替真机验收。
